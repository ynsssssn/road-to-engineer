# 🤖 01. MLOps — 서버리스 ML 파이프라인 구축 및 신뢰성 확보

세탁 서비스 운영에 필요한 두 가지 머신러닝 파이프라인(유저 클러스터링, 수요 예측)을
AWS Lambda 기반 서버리스 환경에서 자동화하고, 그 결과를 Google Sheets 대시보드로
서빙한 뒤, 마지막으로 이 모든 파이프라인이 "제대로 돌았는지"를 사람이 매번 확인하지
않아도 되도록 자동 감지 체계까지 구축한 일련의 프로젝트입니다.

4개 프로젝트를 순서대로 보시면, ML 모델을 처음 서비스에 붙이는 단계부터 시작해서
운영 신뢰성을 확보하기까지의 흐름을 보실 수 있습니다.

---

## 📂 하위 프로젝트

### [01-1. User Clustering](./01-1_USER_CLUSTERING)
`GMM` `AIC 기반 K 자동탐색` `MLOps`

VIP 고객 이탈 방어를 위해 GMM(Gaussian Mixture Model) 기반 유저 클러스터링 파이프라인을
구축하고, 결과를 CRM(Braze) 및 현장 오퍼레이션 시스템에 리버스 ETL로 연동했습니다.

### [01-2. Laundry Forecast](./01-2_LAUNDRY_FORECAST)
`Prophet` `외부 API 연동` `시계열 예측`

기상청 API와 사내 물량 데이터를 결합한 Prophet 기반 수요 예측 파이프라인으로,
YoY 방식 대비 예측 오차를 약 70% 감소시켰습니다.

### [01-3. GAS Data Pipeline](./01-3_GAS_DATA_PIPELINE)
`AWS Lambda` `Google Apps Script` `비용 절감`

Snowflake의 리텐션·코호트 지표를 유료 SaaS 없이 서버리스로 Google Sheets에 자동
연동하여, 연간 약 1,400만 원의 구독 비용을 절감했습니다.

### [01-4. Pipeline Alert Monitoring](./01-4_PIPELINE_ALERT_MONITORING)
`Slack Webhook` `사전 감지형 DQ 모니터링`

위 세 파이프라인이 "에러 없이 실행됐다"와 "결과가 정상이다"가 다르다는 걸 운영하며
깨닫고, 실행 성공 여부뿐 아니라 결과 데이터 자체의 이상치까지 감지해 Slack으로
알리는 공통 모니터링 체계를 구축했습니다.

### [01-5. Data Retention Compliance](./01-5_DATA_RETENTION_COMPLIANCE)
`PyMySQL` `개인정보보호` `ISMS`

ISMS 인증 심사 대응을 위해, 탈퇴 회원의 결제 내역을 5년간 보존 후 개인정보만 마스킹하는
배치를 매일 자동 실행되도록 구축했습니다. 분석·엔지니어링을 넘어 DBA·개인정보보호
영역까지 다뤄본 사례입니다.

## 🔧 그 밖에 대응해본 것

### Airbyte 버전업으로 인한 K8s 인증서 호환성 이슈 대응
Airbyte 버전을 업그레이드하는 과정에서 기존 K8s 클러스터 인증서가 새 버전과
호환되지 않아 Snowflake 적재가 일시 중단된 적이 있습니다. 데이터 엔지니어 부재
상황에서 원인을 인증서 버전 불일치로 특정하고, 호환 가능한 버전으로 맞춰 재기동하여
데이터 유실 없이 복구했습니다.

### 신규 유저 온보딩(Hi-pass) 과정에서 겪은 로그 트래킹의 한계
신규 가입 유저의 첫 구매를 빠르고 저렴하게 유도하는 온보딩 기획(Hi-pass)을 진행하며,
정확한 앱 설치 이벤트를 추적할 방법이 마땅치 않아 "기기에서 앱을 처음 실행하는 순간"을
설치의 대리 신호로 사용해야 했습니다. 특히 iOS는 App Tracking Transparency 정책으로
설치 자체를 추적하기 더 까다롭다는 것도 이 과정에서 체감했습니다. 로그 설계 자체를
주도한 경험은 아니지만, 필요한 로그가 없을 때 분석이 어떻게 막히는지를 직접 겪은
사례입니다.

돌아보면, 디바이스 지문(IDFV 등) 기반 추정이나 애플이 제공하는 SKAdNetwork, 혹은
캠페인 파라미터가 포함된 딥링크처럼 조금 더 정교한 대체 신호를 검토해볼 수 있었을
것 같다는 아쉬움이 남습니다.

### 결제 실패 유저 대상 로그 기반 리텐션 시도
세탁 서비스 특성상 결제가 실패해도 배송은 그대로 진행되는 구조라, 결제 없이 서비스만
이용한 유저가 발생했습니다. 앱 실행 로그와 DB의 LAST_VISIT_AT 컬럼을 함께 확인해
마케팅 수신에 동의한 유저에게 리마인드 push를 보냈지만, 전환율은 1% 미만으로 낮았습니다.
돌아보면, 결제 실패 사유(카드 문제·잔액 부족·결제 중 이탈 등)를 구분하지 않고 유저를
한 그룹으로 뭉뚱그린 게 원인 중 하나였을 것 같습니다.

같은 접근을 구독 갱신 결제 실패(카드 해지·정지, 잔액 부족 등) 유저에게도 적용했는데,
이쪽은 단순 실수와 연장 의지가 있는 유저가 많아 반응이 나쁘지 않았습니다. 이 유저군은
매달 초 약 200명까지 늘었다가 월말에는 약 100명으로 자연스럽게 줄어드는 패턴을
반복했는데, 이 회복이 push 덕분인지 push 없이도 자연 회복됐을 유저인지는 구분하지
못했습니다. 돌아보면, push를 보내는 그룹과 보내지 않는 대조군으로 나눠 A/B로
비교했어야 이 push의 실제 순증 효과를 정확히 말할 수 있었을 것 같습니다.
